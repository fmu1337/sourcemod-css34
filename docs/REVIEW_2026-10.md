## 2. Что нелогично

### 2.1. Задокументированное решение и реальность разошлись

`PATCH_STRATEGY.md` фиксирует «вариант B»: один pin, без параллельных CI-джоб, без слоёв, не делать
`apply-api-compat.sh` / `apply-toolchain.sh` постоянными. В реальности — **пять линий** в CI на каждый
push и де-факто слоистая схема A: `apply-sourcemod.sh` (1.11) → `apply-sourcemod-v112.sh` (1.12+) →
`apply-sourcemod-khook.sh` (KHook), с роутером по `product.version`, а api-compat/toolchain постоянно
включены для rev ≥ 6800. Само по себе это нормально — ненормально, что решение никто не пересмотрел,
и правка в `apply-sourcemod-v112.sh` молча задевает четыре линии сразу. (В доке добавлен статус-блок
с фактической раскладкой.)

### 2.2. Один pin — в 15 файлах

Пин `sm13-latest` (`7472`) встречается в 15 файлах: `versions.env`, `matrix.json` (×3 секции),
`test-server.yml` (8+ матричных строк × 4 поля), `build.yml` (×2), `release.yml`, `release-maintenance.yml`,
два fallback'а в `checkout-deps.sh` / `write-build-stamps.sh`, README, четыре дока. При этом:

- `smoke-test.sh` и `run-smoke.sh` **уже умеют** сами вычислить `SM/MM_VERSION_EXPECT` и коммиты из
  `CSS34_LINE` через `resolve-version.sh`, т.е. `sm_expect / mm_expect / sm_commit / mm_commit` в матрицах
  CI избыточны;
- `check-version-pins.sh` страхует только 2 линии из 5 и не смотрит в `build.yml`;
- fallback'и в `checkout-deps.sh` / `write-build-stamps.sh` срабатывают только при запуске скрипта
  в обход `resolve-version.sh` — а такого пути в репо нет (`write-build-stamps.sh` вдобавок держит
  SM-fallback 7239).

### 2.3. Имя тега кодирует пины, а маппинг тег → линия захардкожен

Тег `1.13.0.7472-mm1.12.0` → `case` в `release.yml` → `CSS34_LINE`. Каждый бамп требует правки workflow,
пересборка требует суффикса `-r<N>`, а установщику всё равно нужен не тег, а `line-<line>`. Информация
«какие пины» уже есть в `versions.env` на коммите тега и в `css34-package.json`.

### 2.4. Две Linux-сборки, и одна из них бесполезна

`build.yml/linux` собирает `sm13-latest` jammy-native (`builder/run/linux.sh` на ubuntu-22.04). Такой
пакет **по дизайну** падает в `check-package.sh`, не грузится в `srcds` на legacy glibc, не тестируется
и не публикуется. Реальная сборка — `legacy-build.sh` в `test-server.yml` и `release.yml`. Итог — лишняя
сборка на каждый push и путаница «какой из двух Linux-пакетов настоящий».

### 2.5. Тулчейн: три компилятора, из которых выбирается не тот, что указан

`legacy-build.sh` ставит gcc-9 и экспортирует `CC=gcc-9`; `builder/run/linux.sh` ставит clang-9 **и**
rom4s clang-10, затем принудительно переключает `CC` на clang-9; `sourcemod.logic.so` собирается
отдельным тулчейном через i386 sysroot (gcc-4.9 libstdc++ для SM < 1.13, gcc-9 для 1.13+);
clang-10 используется только внутри `apply-sourcemod.sh` (SM 1.11), но ставится для всех линий.
Понять, чем собран конкретный `.so`, можно только прочитав четыре скрипта.

### 2.6. CI гоняет то, что не выпускается, и не проверяет то, что заявлено

- `sm11-oldstable` собирается, дымится и гоняет botplay на каждый push, но снят с pointer'ов;
  `sm13-mm20` заморожен навсегда (MM git1407 — последний с SourceHook, SM 7404), но тоже в полной
  матрице (debian:11 / latest, rocky, host, botplay). Это 9 из 24 джоб прогона (и 2 из 5 самых
  долгих botplay) — на линии без развития.
- Сверка vtable-offsets (главная защита от класса багов «неверный offset → краш») реально работает
  только в host-джобе, т.е. не для 1.11 и 1.12 (п. 19).
- Логи падений удаляются в конце прогона (п. 20).
- `test-built-botplay` — ~90 строк с `if: false`.

### 2.7. Значения по умолчанию указывают в прошлое

- `install-addons.sh` без `SM_PACKAGE` / `MM_PACKAGE` молча качает rom4s SM 6572 + MM 1.10.6 — локальный
  «smoke» может проверить вовсе не наш пакет.
- `smoke-test.sh` / `run-smoke.sh` в крайнем fallback ждут SM 1.11.0.6970 + MM 1.10.7, хотя default-линия
  `sm13-latest`; `install-addons.sh` ищет built MM в `deps/mmsource-1.10`.
- `cleanup-artifacts.yml`: код по умолчанию держит 48 ч, но и dispatch, и schedule передают `0`.

## 3. Предложения по упрощению

Порядок — по соотношению «польза / усилия». Пункты 1–6 — часы, каждый отдельным маленьким PR.

### Быстрые (часы)

1. **Удалить мёртвое** из таблицы 2.8 (кроме диагностики, которую стоит перенести в
   `testing/scripts/diag/` с одной строкой README). Минус ≈1800 строк.
2. **`build.yml/linux` → убрать** (или перевести на `legacy-build.sh`). Все линии уже собираются
   правильно в `test-server.yml`.
3. **Починить версию Metamod**: передавать `MMS_GIT_REV` в версионирование MM так же, как
   `SOURCEMOD_GIT_REV` в SM (или `fetch --depth` с запасом), и проверять в smoke полную строку
   `1.12.0-dev+1226`, а не `1.12.0`.
4. **Логи падений**: в `cleanup-workflow-storage` удалять артефакты только при успешном прогоне
   (`if: success()`), retention 1 день и так ограничивает квоту.
5. **vtable-check везде**: добавить `python3` и `binutils` в `install-deps.sh` — тогда сверка offsets
   заработает для всех линий и дистрибутивов.
6. **Убрать корневые симлинки** `*.tar.gz` из `builder/run/{linux,windows}.sh` (или делать их
   относительными) и `mmsource-*.tar.gz` в `.gitignore`; одно имя Windows MM-ассета с `git<rev>`.

### Средние (дни)

7. **Один источник правды для пинов.** Сделать `builder/scripts/lines.sh --json`, который из
   `versions.env` печатает матрицу `[{line, sm_version, sm_commit, mm_version, mm_commit, …}]`.
   Первая джоба workflow отдаёт её в `outputs`, остальные берут `matrix: ${{ fromJSON(...) }}`.
   В шаги передавать только `CSS34_LINE` — `smoke-test.sh` сам вычислит ожидания. После этого
   из `test-server.yml` / `build.yml` уходят все SHA и версии, `check-version-pins.sh` сжимается до
   проверки README / `matrix.json` (или они генерируются тем же скриптом), fallback'и в
   `checkout-deps.sh` / `write-build-stamps.sh` удаляются (fail fast без `resolve-version.sh`).
8. **Тег → линия без `case`.** Варианты: (a) тег `<line>-<YYYYMMDD>[.N]` (`sm13-latest-20261013`),
   пины читаются из `versions.env` на коммите тега, версии — в заголовке релиза; (b) оставить текущий
   формат, но в `release.yml` искать линию, у которой `1.<maj>.0.<rev>-mm<mm>` совпадает с тегом.
   Оба убирают правку workflow при каждом бампе.
9. **Сжать `test-server.yml`** (1267 строк): composite action «restore packages + server tree + docker run
   <script>» вместо ~10 копий одного и того же; ключ кэша сервера (сейчас 11 копий одной строки) — в
   одном месте.
10. **Пересобрать матрицу по ценности.** На push / PR: build + `debian:11` smoke + botplay для живых
    линий (`sm13-latest`, `sm12-latest`, `sm13-mm20-khook`). Раз в неделю и на теги: всё остальное
    (`debian:latest`, rocky, host, extra distros) и замороженные `sm13-mm20`, `sm11-oldstable`.
11. **Доки:** один язык; README — только «что ставить / известные проблемы / как собрать»;
    `docs/MAINTAINING.md` — CI, релизы, бамп пинов (сюда же содержимое `JULES_DAILY_VERSION_BUMP.md`);
    `docs/lines/<line>.md` — по одному на линию; `docs/history/` — PATCH_STRATEGY-обсуждения,
    BYTE_MATCH, V34_COMPARISON, 6522, field report. `matrix.json` оставить для `compatibility` /
    `reference`, а `releases` / `lines` генерировать или убрать (источник правды — Releases и `lines.json`).
